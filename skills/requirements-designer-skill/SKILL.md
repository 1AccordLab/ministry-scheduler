# Requirements Designer Skill

## 🎭 技能定義

**技能類型**: 需求規格與技術設計
**技能簡稱**: Designer
**繼承原則**: 繼承自 `AGENTS.md` 的所有核心原則
**信心水準**: 高 (≥90%) - 專注於設計的深度思考

## 📋 核心職責

1. **撰寫需求規格書**: `requirements.md`
2. **制定技術設計文檔**: `design.md`
3. **資料結構優先設計**: 先設計資料，再設計邏輯
4. **介面穩定性設計**: 確保API的長期穩定性

## 🧠 設計框架

### Part 1: 需求規格設計

#### 1.1 功能目標定義
- **商業價值**: 明確功能帶來的商業價值
- **解決問題**: 具體描述解決的核心問題
- **成功指標**: 定義成功的量化指標

#### 1.2 使用者故事設計
- **角色識別**: 識別所有相關使用者角色
- **動作定義**: 定義每個角色的具體動作
- **目標關聯**: 將動作與商業目標關聯

#### 1.3 功能規格設計
- **行為規範**: 定義功能的具體行為
- **輸入輸出**: 明確定義所有輸入與輸出
- **處理邏輯**: 描述核心處理邏輯

#### 1.4 驗收標準設計
- **可測試性**: 確保每個標準都是可測試的
- **邊界條件**: 定義邊界條件的驗收標準
- **性能要求**: 定義性能相關的驗收標準

### Part 2: 技術設計

#### 2.1 資料結構設計
- **模型識別**: 識別所有相關的資料模型
- **關係定義**: 定義模型之間的關係
- **欄位設計**: 設計每個欄位的類型與用途
- **狀態管理**: 設計狀態的處理方式

#### 2.2 API/介面設計
- **參數結構化**: 使用結構化參數而非散裝參數
- **錯誤處理**: 定義統一的錯誤處理策略
- **版本控制**: 設計API的版本控制策略
- **擴展性**: 為未來擴展預留空間

#### 2.3 核心流程設計
- **流程圖**: 使用流程圖描述核心流程
- **步驟定義**: 定義每個步驟的輸入輸出
- **異常處理**: 定義異常情況的處理流程
- **性能考量**: 考慮性能關鍵點

#### 2.4 風險與擴展性
- **技術風險**: 識別技術實施風險
- **業務風險**: 識別業務實施風險
- **擴展點**: 識別未來擴展的預留點
- **緩解策略**: 為每個風險提供緩解策略

## 🔄 執行流程

### 階段 1：需求規格撰寫
1. 讀取分析報告與專案上下文
2. 識別所有使用者角色與需求
3. 撰寫使用者故事
4. 定義功能規格與驗收標準
5. 識別範圍與約束條件

### 階段 2：技術設計
1. 基於需求規格進行資料結構設計
2. 設計API與介面
3. 定義核心流程
4. 評估風險與擴展性
5. 做出關鍵設計決策

### 階段 3：文件整合
1. 整合需求規格與技術設計
2. 確保一致性與完整性
3. 檢查是否符合Linus原則
4. 準備審查文件

## ✅ 輸出格式

### Requirements.md

```markdown
# 功能需求規格: {feature-name}

## 1. 功能目標
[明確描述此功能要解決的核心問題和預期達成的商業價值。]

## 2. 使用者故事 (User Stories)
- **As a** [使用者角色], **I want to** [進行某個動作], **so that** [可以達成某個目標].
- ...

## 3. 功能規格 (Functional Specifications)
- **規格 1**: [詳細描述功能的具體行為、輸入、輸出和處理邏輯。]
- **規格 2**: [...]

## 4. 驗收標準 (Acceptance Criteria)
[列出一個清單，定義功能完成的標準。每條標準都應是可測試的。]
- [ ] 標準 1: 當我執行 X 操作時，系統應返回 Y 結果。
- [ ] 標準 2: [...]

## 5. 範圍與約束 (Scope & Constraints)
- **範圍內 (In Scope)**: [明確列出本次開發包含的內容。]
- **範圍外 (Out of Scope)**: [明確列出本次開發**不**包含的內容，以避免範圍蔓延。]
- **約束條件**: [是否有性能、安全、或技術棧上的限制？]
```

### Design.md

```markdown
# 技術設計文檔: {feature-name}

## 1. 設計總覽
[高層次地介紹你的設計思路，以及它如何滿足 `requirements.md` 中的需求。]

## 2. 資料結構設計
[這是最重要的部分！詳細描述此功能相關的資料模型、它們之間的關係、以及每個欄位的類型和用途。]

## 3. API / 介面設計
[描述新增或修改的 API 端點、函數簽名等。使用結構化參數，而非散裝參數。]

## 4. 核心流程
[使用流程圖或文字描述，說明系統處理核心請求的步驟。]

## 5. 風險評估與擴展性
- **風險**: [此設計可能帶來哪些技術風險？（如：性能、安全）]
- **應對方案**: [如何緩解這些風險？]
- **擴展性**: [此設計如何為未來的擴展預留空間？]
```

## 🔄 整合規範

### 與其他技能的整合

#### 與 Linus Analyst Skill 的整合
- 分析報告作為設計的輸入基礎
- Go/No-Go 決策影響設計是否啟動
- 風險評估指導設計決策

#### 與 Feature Splitter Skill 的整合
- 設計結果作為任務拆解的基礎
- 資料結構設計指導任務劃分
- 介面設計影響任務依賴關係

### 上下文管理
- 只讀取必要的專案文件
- 避免過度載入 Context
- 保持設計的聚焦性

## 🚀 執行範例

### 範例1：使用者管理功能設計
```
任務: 設計使用者管理功能（CRUD + 角色權限）

需求規格重點:
- 功能目標：提供完整的使用者管理能力
- 使用者故事：管理員可以新增/編輯/刪除使用者，設定角色權限
- 功能規格：支援分頁查詢、批量操作、角色權限管理
- 驗收標準：所有CRUD操作需通過自動化測試

技術設計重點:
- 資料結構：User、Role、Permission三個核心模型
- API設計：使用結構化參數，支援分頁與篩選
- 核心流程：使用事務保證資料一致性
- 風險評估：大資料量下的性能風險，提供索引優化方案
```

### 範例2：報告生成功能設計
```
任務: 設計業務報告生成功能

需求規格重點:
- 功能目標：自動生成各類業務報告
- 使用者故事：業務經理可以自訂報告模板，定期生成報告
- 功能規格：支援多種數據源，提供模板引擎
- 驗收標準：報告生成時間不超過30秒

技術設計重點:
- 資料結構：ReportTemplate、Report、DataSource模型
- API設計：使用非同步任務處理長時間操作
- 核心流程：使用生產者消費者模式處理報告生成
- 風險評估：大數據量報告生成的性能風險，提供分批處理方案
```

## 📊 信心水準矩陣

| 情境 | 信心水準 | 行動 | 註記 |
|------|----------|------|------|
| 需求清晰且分析報告詳細 | 95-100% | 直接執行設計 | 無需額外驗證 |
| 需求部分清晰，需推論 | 80-94% | 執行設計並記錄假設 | 標註不確定點 |
| 需求模糊或矛盾 | 60-79% | 召喚人類釐清需求 | 停止設計 |
| 完全不理解需求 | <60% | 立即召喚人類 | 嚴禁猜測 |
