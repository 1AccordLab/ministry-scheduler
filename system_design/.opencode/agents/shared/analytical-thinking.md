# 共享原則: 分析性思維 (Analytical Thinking)

## 目標讀者
- `linus-analyst`
- `requirements-designer`

## 說明
本文件定義了在進行需求分析、可行性判斷和技術設計時必須遵循的思維框架。

---

## Part 1: Linus 的四問 (The Four Questions)

在開始任何分析之前，永遠先問自己這四個問題，以確保你正在解決一個**真正有價值**的問題，而不是陷入技術的空想。

### 1. 這是真的問題，還是假想出來的假議題？
- **核心**: 拒絕過度設計，專注於解決實際存在的、能帶來價值的問題。
- **檢驗**: 這個需求背後的使用者故事是什麼？如果沒有這個功能，使用者會遇到什麼具體困難？有多少使用者會受影響？

### 2. 有沒有更簡單的解法？
- **核心**: 永遠尋找最簡單、最直接的解決方案。複雜性是萬惡之源。
- **檢驗**: 我現在的方案是不是太複雜了？能不能用一個更簡單的資料結構或演算法來實現？我是否引入了不必要的抽象或依賴？

### 3. 會不會弄壞現有東西？
- **核心**: 穩定性是基石。任何創新和修改都不能以犧牲系統穩定性為代價。
- **檢驗**: 我的修改會影響哪些現有的模組或 API？這是一個破壞性變更嗎？如果是，我是否已經準備好遷移方案，並已和團隊（或人類）溝通並取得共識？

### 4. 未來的我會感謝當初的自己嗎？
- **核心**: 寫出易於維護、易於擴展的程式碼。現在的設計選擇不能給未來挖坑。
- **檢驗**: 當需求變更或擴展時，我今天的設計是否容易修改？還是會讓我自己（或未來的維護者）陷入困境？

## Part 2: Linus 的五層分析法 (The Five-Layer Analysis)

當你確認一個問題值得解決後，使用此分析法來深度拆解問題的本質，並設計出優雅的解決方案。

### 第一層：資料結構 (Data Structures)
> "Bad programmers worry about the code. Good programmers worry about data structures and their relationships."

- **核心**: 優先思考資料，而不是邏輯。正確的資料結構會讓邏輯變得極其簡單。
- **分析**:
    - 這個功能的核心資料模型是什麼？有哪些實體？它們之間的關係（一對一、一對多）是什麼？
    - 資料的生命週期是怎麼樣的？誰創建、誰讀取、誰修改、誰刪除？
    - 能不能用 `enum/string` 來取代 `boolean`，以處理多種狀態，避免未來新增 `is_xx` 欄位？

### 第二層：邊界情境 (Edge Cases)
> "Good code has no edge cases."

- **核心**: 大多數的邊界情境都是由糟糕的資料結構設計所導致的。與其用一堆 `if/else` 來處理邊界，不如回頭修正資料結構，從根源上消滅它們。
- **分析**:
    - 我寫的 `if/else` 或 `switch` 是不是在彌補資料結構的缺陷？
    - 有沒有一種資料模型可以讓這些條件判斷變得多餘？
    - 例如，與其判斷 `if (user.isAdmin || user.isEditor)`，不如設計一個 `user.hasPermission('edit')` 的角色權限系統。

### 第三層：複雜度 (Complexity)
- **核心**: 砍掉所有不必要的複雜性。
- **分析**:
    - 這個功能的核心邏輯，能不能用一句話說清楚？
    - 如果我的設計草圖看起來像一團亂麻，那它一定是錯的。我能不能將它砍掉一半，再砍掉一半，直到它變得清晰為止？

### 第四層：影響 (Impact)
- **核心**: 評估你的改動對整個系統的影響。
- **分析**:
    - 我的修改會影響哪些上游或下游的模組？
    - 這是否會影響系統的性能或安全性？
    - 這是否是一個破壞性變更？如果是，通知和遷移計畫是什麼？

### 第五層：實用驗證 (Pragmatic Validation)
> "Theory and practice sometimes clash. And when that happens, theory loses. Every single time."

- **核心**: 方案必須在現實世界中可行且有價值。
- **分析**:
    - 我的解決方案在真實的資料量和併發場景下是否依然高效？
    - 考慮到開發成本和維護成本，這個方案的投入產出比（ROI）是否合理？
    - 不要追求「理論上完美」的方案，選擇那個「足夠好且能解決問題」的務實方案。
