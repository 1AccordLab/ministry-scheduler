# 共享原則: 文件撰寫 (Documentation Authoring)

## 目標讀者
- `requirements-designer`
- `developer-agent`

## 說明
本文件提供了 AI 開發團隊在不同階段產出各類文件時，必須嚴格遵守的標準模板。統一、清晰、完整的文件是 AI 高效協作的基石。

---

## Part 1: 文件撰寫的核心原則

1.  **精確性優先於簡潔性**: 如果簡化用詞會造成理解歧義，選擇完整、無歧義的表達。
2.  **擴展性優先於短期便利**: 在描述架構時，明確標註為未來擴展預留的設計點。
3.  **避免模糊表達**: 嚴禁使用 "適當的"、"必要時" 等模糊詞語，必須提供具體的標準或觸發條件。

---

## Part 2: `requirements.md` 模板

**由 `requirements-designer` 撰寫**

```markdown
# 功能需求規格: {feature-name}

## 1. 功能目標
[簡要描述此功能要解決的核心問題和預期達成的商業價值。]

## 2. 使用者故事 (User Stories)
- **As a** [使用者角色], **I want to** [進行某個動作], **so that** [可以達成某個目標].
- ...

## 3. 功能規格 (Functional Specifications)
- **規格 1**: [詳細描述功能的具體行為、輸入、輸出和處理邏輯。]
- **規格 2**: [...]

## 4. 驗收標準 (Acceptance Criteria)
[列出一個清單，定義功能完成的標準。每條標準都應是可測試的。]
- [ ] 標準 1: 當我執行 X 操作時，系統應返回 Y 結果。
- [ ] 標準 2: [...]

## 5. 範圍與約束 (Scope & Constraints)
- **範圍內 (In Scope)**:
  - [明確列出本次開發包含的內容。]
- **範圍外 (Out of Scope)**:
  - [明確列出本次開發**不**包含的內容，以避免範圍蔓延。]
- **約束條件**:
  - [是否有性能、安全、或技術棧上的限制？]
```

## Part 3: `design.md` 模板

**由 `requirements-designer` 撰寫**

```markdown
# 技術設計文檔: {feature-name}

## 1. 設計總覽
[高層次地介紹你的設計思路，以及它如何滿足 `requirements.md` 中的需求。]

## 2. 資料結構設計
[這是最重要的部分！詳細描述此功能相關的資料模型、它們之間的關係、以及每個欄位的類型和用途。]

## 3. API / 介面設計
[描述新增或修改的 API 端點、函數簽名等。使用結構化參數，而非散裝參數。]

## 4. 核心流程
[使用流程圖或文字描述，說明系統處理核心請求的步驟。]

## 5. 風險評估與擴展性
- **風險**: [此設計可能帶來哪些技術風險？（如：性能、安全）]
- **應對方案**: [如何緩解這些風險？]
- **擴展性**: [此設計如何為未來的擴展預留空間？]
```

## Part 4: `task.md` 模板

**由 `developer-agent` 撰寫**

```markdown
# 任務計畫: {task-name}

**所屬功能**: {feature-name} (如有)

## 🎯 任務目標
[列出此單一任務要達成的、具體且可驗證的目標。]

## 🧠 設計與執行思路
[簡要描述你將如何實現這個任務，特別是關鍵的技術決策。]

## 📋 詳細執行步驟
[按照實際執行順序列出你的 TDD 步驟。]
1.  **測試**: 編寫一個驗證 [某個功能點] 的失敗測試。
2.  **實作**: 編寫程式碼讓上述測試通過。
3.  **重構**: ...
4.  **測試**: 編寫下一個失敗測試...

## 🤔 中等信心決策 (如有)
[列出你做出的、信心水準在 70-89% 的決策。]
- **假設**: [我假設使用者偏好 X 行為，因為...]
- **不確定點**: [我對 Y 部分不太確定，建議後續驗證...]

## 🚨 破壞性變更 (如有)
[列出會影響現有功能的改動及其影響範圍。]
```

## Part 5: `changes.md` 模板

**由 `developer-agent` 在開發完成後撰寫**

```markdown
# 變更記錄: {task-name}

## 📁 檔案變更摘要

### 新增
- `path/to/new-file.ts`: [理由]

### 修改
- `path/to/modified-file.ts`: [變更摘要]

### 刪除
- `path/to/deleted-file.ts`: [理由]

## 💻 核心程式碼變更
[（可選）附上最關鍵的程式碼片段 diff，以幫助審查者快速理解核心變動。]
```

---

## Part 6: `review.md` 模板

**由 `developer-agent` 在開發完成後生成**

```markdown
# 審查清單: {task-name}

## ✅ 核心功能檢查
- [ ] 任務目標是否全部達成？
- [ ] 功能是否符合 `requirements.md` 的描述？

## 🎨 程式碼品質檢查
- [ ] 是否遵循 `development-discipline.md` 中的所有風格指南？
- [ ] 縮排是否超過 3 層？
- [ ] 資料結構設計是否優雅？
- [ ] 是否存在不必要的複雜性？

## 🚨 風險與影響檢查
- [ ] 是否有未記錄的破壞性變更？
- [ ] 是否已通過所有專案定義的自動化檢查 (lint, tests)？

## 🤔 需要人類確認的項目
[列出你在 `task.md` 中記錄的、需要人類特別關注的中等信心決策或假設。]
```
